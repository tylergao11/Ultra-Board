# 每日数据更新契约

## 唯一入口

```powershell
npm run data:update
npm run data:update -- --date YYYY-MM-DD
```

默认模式读取同花顺官方复盘首页内嵌的有效 `Global.date`，把已经公开收盘复盘的最新交易日作为目标。显式 `--date` 严格执行指定日期；来源未发布、日期不一致或合同不完整时直接停在该日。

## 流程与提交边界

更新按以下顺序运行：

`目标日解析 → 开盘啦日快照 → 同花顺涨停池 → 同花顺故事 v1/v2 → 单日完整性校验`

来源采集只写入各自 canonical 日目录，便于失败后定位和续跑，不再额外生成发布快照。更新锁 `data/.daily_update.lock` 避免同一工作区并发刷新。

## 完整性门禁

目标日必须满足以下条件：

- 开盘啦 `_DONE` 存在、`_MISMATCH` 不存在，四个正式快照文件可读；
- 同花顺涨停池合同可读；
- 单日 canonical 故事文件可读；
- KPL、同花顺涨停池和自动逐股故事的股票集合闭合；
- 每只正式股票都有非空逐股故事；
- `build_day_component` 能从上述来源即时组装目标日，且 `source_issues` 为空。

更新入口不会静默跳过目标日；任一来源缺失、日期错位或股票集合不闭合都会直接失败。

## 故事来源

历史 v1 文件继续读取人工核对的同花顺“最强风口”长图。新增日默认生成 v2：

- 官方历史复盘页 `block_1890`：日级主流看点；
- 官方历史复盘页 `block_1891`：日级盘面脉络；
- 官方涨停池 `reason_type`：逐股涨停原因原文。

v2 会校验请求日期、页面最后一个有效 `Global.date`、目标区块唯一性、分页总数、名码唯一性、非空故事和三方股票集合，并记录 URL、抓取时间与响应摘要。同一天只有一个 canonical 故事文件；已经人工核对的 v1 文件优先保留。

这些字段反映供应商的收盘复盘归因，不能证明相关事件在 15:00 前公开。个股题材、题材索引和题材筛选仍只来自开盘啦 `theme/themes`；`reason_type` 保持整串原文，不按 `+` 拆分。
