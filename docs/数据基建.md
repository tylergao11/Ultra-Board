# 数据基建

交易讨论只以根目录AGENTS.md及用户最新指示为准。本文件只定义数据怎么取、字段是什么意思。

## 复盘的三个数据入口

统一命令：`python -m ultraboard.kaipanla.query`。

| 目的 | 接口或字段 | 使用方式 |
|---|---|---|
| 找属性编号 | `GetConceptJXBKw23 / StockF10Basic` 的CCode、CName | 根据已经认定的炒作属性找对应编号；Analysis是当前说明，不回填历史 |
| 全部属性成员 | `ZhiShuStockList_W8 / ZhiShuRanking` | Date、PlateID、Index，st=50、old=1、Type=6；完整分页后与同日涨停池取交集 |
| 当日涨停名单 | 已保存的 `DailyLimitPerformance` | 包括首板与换手板；主分类不用于删除成员 |
| 供应商一字标记 | `GetZhangTingTianTi / FuPanLa` 的StockList[6] | 直接保留0/1，不根据日线重算，也不以9:25首封替代 |

历史接口地址：`https://apphis.longhuvip.com/w1/api/index.php`。请求版本与DeviceID统一复用`ultraboard/kaipanla/client.py`，不重复创建身份或另写请求客户端。

```powershell
python -m ultraboard.kaipanla.query concepts 000533 --name 数据中心
python -m ultraboard.kaipanla.query breadth --plate 801460 --before 2024-12-30 --day 2024-12-31
python -m ultraboard.kaipanla.query pool 2024-12-31 --marked-only
python -m ultraboard.kaipanla.query pool 2025-01-02 --code 000533
```

数量是成员代码与涨停代码的交集，不是成分总数，不是栏目数字，也不只数一字。支持`--json`取得结构化结果。查询模块不认定主属性、不自动确定节点或持仓。

## 缓存和核验

- `data/kaipanla/raw/YYYY-MM-DD/zt_pool.json`：当天涨停池，原有唯一来源。
- 同目录`limit_ladder.json`：供应商涨停天梯原始返回，补充一字标记。
- `data/kaipanla/plate_members/YYYY-MM-DD/板块编号.json`：完整成员及原始分页。
- `data/kaipanla/concepts_current/抓取日期/股票代码.json`：当前属性与编号查询缓存。
- 日期、代码唯一性、分页总数和交集股票价格需一致。空响应报缺口，不能输出零只。
- 成员接口st=1000曾返回成功码但空列表；已采用实测可用的50条分页，不重复探测。
- 成员接口中的历史行情日期可验证，附带名称、标签和成员关系是否存在后补没有完整保证；保持`historical_membership_verified=false`，不宣称绝对不漂移。
- 天梯第6项的供应商含义为“大单一字”标记。1直接记录为有标记，0记录为未标记；不能另造“大单封单阈值”，也不能将0冒充独立证明非一字。个别来源冲突才抽查，不能重新铺开逐股日线工程。
- 实测：顺钠2024-12-31标记1，2025-01-02标记0。两日数据中心交集为8只、5只，完整名单见接续记录。
- `GetPlateInfo_w38`是最新涨停原因列表，会忽略历史日期，不能替代历史成员接口。`GetDayZhangTing`本次也未按传入日期定位，不作为指定日板型查询。
- `HisDaBanList`当前封装的PidType=2为炸板列表，不是完整涨停池；不能拿它的空值或数量代替上述正式涨停池。

## 其他事实来源

| 数据 | 来源 | 边界 |
|---|---|---|
| 当日粗分类与梯队 | 开盘啦theme、raw、sector_ladder | 供应商展示，非完整成员集合 |
| 价格、封单、首末封、炸板次数、详细板型 | 同花顺limit_pool | limit_up_type直接返回一字板/T字板/换手板；不由OHLC构造 |
| 触板未封 | 同花顺open_limit_pool | 与收盘涨停名单区分 |
| 逐股涨停原因和市场复盘 | 同花顺stories | 保留原文及发布时间边界，供消息核对，不直接拆标签计板块 |
| 当前完整概念与股本 | 同花顺stock_profiles | 仅当前快照，不能回填历史属性 |
| 竞价事实 | data/research/auction | 有当时时间与来源的记录；收盘封单不当成竞价封单 |
| 最近交易日分时 | 东方财富intraday_ticks | 三秒样本，不自动推导带动关系 |
| 留存价格检查数据 | data/price_checks | 仅冲突抽查，复盘查询不自动读取 |

同花顺板型是已有结构化来源，但2024-12-31的历史接口本次返回status_code=-1，不能保证所有早期日期可取。开盘啦标记查询独立于同花顺日线和完整日更新，不因此重复下载行情。

日数据维护流程另见[每日数据更新契约](每日数据更新契约.md)。原始资料只作为证据，不提供交易规则。

接口调用参考：[板块成分调用源码](https://github.com/fleetinglife/levistock/blob/main/levistock/sector/sector_stocks_his_kph.py)、[天梯字段源码](https://github.com/fleetinglife/levistock/blob/main/levistock/stock/stock_fupanla_kph.py)。参数与字段以本项目实际返回核验为准，不照搬第三方的交易解释。

## 连续复盘网站的数据源优化（2026-09-14 核验）

本节记录本次接口核验与后续采集调整建议，不表示更新程序已经切换。现行执行流程仍见《每日数据更新契约》，交易讨论仍以根目录 AGENTS.md 为准。

### 实际取数结果

原始响应保存在 [本次核验记录](../artifacts/source-audit-20260914.json)，记录请求日期、抓取时间及响应正文；本次未覆盖原有正式日缓存。

| 检查 | 本次结果 | 可以得出的结论 |
|---|---|---|
| 开盘啦当前 `DailyLimitPerformance` 的 PidType=1～5 | 2026-09-14 共 55 只且代码无重复，首封时间戳均属于当天；价格、成交额、换手率均非空 | 当前直接涨停池可以承担核心股票行情；此为单日样本，不等于所有日期已验证 |
| 同花顺同日涨停池对照 | 55 只，股票代码集合与上述开盘啦完全一致 | 本次样本支持取消同花顺涨停池作为第二套日常必备名单；不表示两家每个字段都完全相等 |
| 开盘啦 2025-03-06 首板池与本地原始行对照 | 本次 96 行，其中 93 只与原有正式股票匹配；24 只附带标签 raw[12] 不同，主分类 raw[5]、首封 raw[4]、价格 raw[21] 在这 93 只中未见差异 | 附带标签不能视作不变的历史原貌；本次没有证明主分类或完整板块成员发生漂移 |
| 开盘啦历史天梯 | 请求 2025-03-06，返回 Date=2025-03-06、108 只 | 这个样本的日期与股票天梯可用；大单一字标记仍按供应商原义保存 |
| 现有 `HisDaBanList` 封装 | 分别请求 2025-03-06、2026-09-08，均返回 day=2026-09-14、空列表；同时显式传 Date 后仍相同 | 现有封装不可作为指定日期炸板池；成功码和空列表不能证明历史当天没有炸板，不据此断言开盘啦没有其他可用接口 |
| 同花顺炸板池 | 2026-09-08 日期校验通过、37 只；2025-03-06 返回 status_code=-1 | 近期补充路径可用，早期覆盖仍有缺口，不能承诺全历史可补齐 |
| 开盘啦最新涨停原因 `GetPlateInfo_w38` | 本次返回 2026-09-14、空列表，而同日直接涨停池有 55 只 | 涨停原因缺失不能当成涨停名单为空；原因接口不应阻断已完整取得的核心行情 |

标签差异举例：同为 2025-03-06 的国脉科技，保存的 raw[12] 是“海峡两岸、数据确权”，本次返回“6G、数据确权”；其主分类仍为“人工智能”。这里比较的是已保存响应与本次响应，不能据此认定哪份标签就是当日首次发布版本。

### 建议的最小来源组合

| 内容 | 主要来源 | 补充与边界 |
|---|---|---|
| 题材名称、板块编号、完整成员 | 开盘啦 | 保存每次取得的版本；供应商粗分类、附带标签、完整成员分开，不按多家标签拼接计数 |
| 每日涨停名单、连板数、基础行情 | 开盘啦直接涨停池 | 同花顺用于异常或缺口核对，不要求每次为同一批字段重复全量采集 |
| 一字与接力过程 | 开盘啦已核验标记优先 | “大单一字=0”不等于确定非一字；精确板型、末封、开板次数的替代字段未核验，所需字段缺失时显式补源 |
| 炸板失败 | 先保留已通过日期校验的同花顺炸板池 | 开盘啦现有封装尚不可用；早期缺口查打板客并记录来源，不能仅凭网页可读便声称完整批量采集已具备 |
| 涨停原因、催化 | 开盘啦原因和盘面梳理优先，必要时核对消息原始发布 | 收盘解释与消息首次公开时间分别记录；缺少原因可显示待补，不阻断已完整的股票行情 |
| 交易日 | 交易所休市安排与可校验的交易日历 | 不能把周一至周五全部当交易日，也不能把本地相邻两个文件夹当成相邻交易日 |
| 分时、全套 F10、龙虎榜等辅助资料 | 按具体页面需要取数 | 不作为第一版核心连续复盘的每日必备项 |

交易日依据：[上交所 2026 年休市安排](https://www.sse.com.cn/disclosure/dealinstruc/closed/c/c_20251222_10802510.shtml)、[深交所 2026 年部分节假日休市安排](https://investor.szse.cn/disclosure/notice/general/t20251222_618087.html)。

### 调整顺序

1. **先保护连续性。** 每份记录保留交易日期、实际抓取时间、来源接口与参数、原始响应；复抓保留新版本，不覆盖先前版本。历史补采标为补采，不能冒充当日快照。股票使用代码身份，题材使用供应商编号；名称变化单独记录。分类口径调整与股票新涨停分别记录，不能把标签扩容直接当成市场加强。
2. **补齐失败状态与日历。** 每日同时覆盖涨停与触板未封；对昨日仍在跟踪、今天不在两池中的股票保留记录，核实交易状态，缺数据不直接判作断板。按交易日历显示缺失日，禁止跨过缺口悄悄连接为连续两天。
3. **收窄核心更新。** 核心行情、板块成员、失败状态按各自完整性发布；某板块成员不全时不计算它的宽度变化。消息或辅助资料缺失仅影响相应模块，不把整日行情一起判作不可用。先保证正在追踪的题材能够逐日取得完整成员，再扩展覆盖。
4. **移除重复的强制依赖。** 核验覆盖足够后，再将同花顺涨停池、完整 F10、东方财富秒级分时改成按需补充。当前 `daily_update.py`、`day_facts.py` 的完整性判断及日期选择仍依赖多个来源，不能只删缓存或跳过某一步便宣称迁移完成。

现有代码中，`day_facts._neighbor_day` 使用已有数据日期列表，遇到所有来源均缺失的一天会跳过；`kaipanla.backfill.trading_days` 只筛选工作日。这两处需要在网站连续回放接入时改用真实交易日历。本次只完成来源核验和方案记录，没有修改上述运行逻辑。
