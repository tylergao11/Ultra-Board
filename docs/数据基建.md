# Ultra-Board 数据基建方案

> 状态：方案有效；**主链路已实现**（回灌 / 开盘价补全 / 梯队日材料）。启动见根 `README.md`。
> 最后更新：2026-08-04

---

## 一、项目定位

连板打法的量化辅助系统。**只做连板，首板不参与决策**，仅作为气氛组统计其数量与属性分布。

工作流三段式：

| 阶段 | 时点 | 做什么 |
|---|---|---|
| 复盘选股 | 当日 18:00 后 | 定题材属性、排连板梯队、评估发酵能力，产出次日候选池 |
| 竞价判断 | 次日 09:25 | 用竞价数据判定超预期 / 不及预期 / 大坑 |
| 打板确认 | 次日盘中 | 人工执行 |

核心特征是**延迟容忍**：不需要实时行情，需要的是准确的复盘数据和确定的竞价结果。

跟踪池规模：连板股每日 10~30 只，加候选不超过 150 只。

## 二、数据源决策

### 2.1 为什么不走交易所官方源

下午花了大量时间验证交易所官方接口，最终**否决**。记录理由，避免以后重走。

否决依据有三条：

**延迟优势归零。** 官方源唯一的优势是数据链路少一环，但本项目延迟容忍。竞价结果在 9:25 撮合完即为确定值，晚 30 秒拿到的是同一个数。

**准确性上第三方并不差。** 实测同一时刻的贵州茅台：上交所官方、东财、新浪、腾讯四个源给出的今开均为 1350.06，分毫不差。竞价成交量 23500 股，用东财成交额 31,726,410 反推得 1350.06，完全吻合。这类价量数据本就源自交易所馈送，中间无加工失真。

**字段严重不足，这是决定性的。** 官方只给价量，不给连板数、封板时间、炸板次数、封板资金、所属行业、涨停原因。这些要么得从日 K 和分时硬算，要么根本算不出来。

另外需要澄清一个认知误区：上交所的 `yunhq.sse.com.cn:32041` **本质上和东财是同一性质**——都是给自家网站前端用的接口，同样没有公开文档、没有 SLA、同样可能说改就改。"官方"这个标签的分量没有想象中重。

### 2.2 最终数据源分工

| 层 | 数据源 | 产出 | 时点 |
|---|---|---|---|
| 复盘层 | 开盘啦 | 题材归因、梯队、情绪温度 | 18:00 后 |
| 打板基础层 | akshare（东财四池） | 连板数、封板时间、炸板次数、封板资金、行业 | 收盘后 |
| 竞价层 | **待定**（东财或交易所） | 9:25 竞价价量 | 次日 09:25 |
| 校验层 | 交易所官方 | 抽样复核涨停价与连板数 | 按需 |

**开盘竞价不走开盘啦**，其实时接口已有反爬（见 4.3）。两条线互相独立，一条挂了不影响另一条。

## 三、已验证的接口

### 3.1 akshare（版本 1.18.81）

一个请求 1.05 秒拿到全市场涨停池，覆盖沪深北三市。

| 函数 | 内容 | 实测（2026-08-04） |
|---|---|---|
| `stock_zt_pool_em` | 涨停池 | 138 只 |
| `stock_zt_pool_previous_em` | 昨日涨停池 | 75 只，带昨日封板时间、昨日连板数 |
| `stock_zt_pool_zbgc_em` | 炸板池 | 15 只 |
| `stock_zt_pool_strong_em` | 强势股池 | 82 只，带量比、是否新高 |

涨停池字段：`连板数`、`首次封板时间`、`最后封板时间`、`炸板次数`、`封板资金`、`涨停统计`、`换手率`、`成交额`、`流通市值`、`所属行业`。

**封板资金这个字段很关键**——早先判断"任何官方源都没有历史封单、必须自己积累"，实际上东财四池直接提供，该缺口不存在。

交叉验证：恒银科技（603106）用上交所官方日 K 算得 3 板 T 字板；涨停池给出连板数 3、涨停统计 3/3、首封 09:25:00、末封 09:30:42、炸板 1 次。两者完全吻合，同时证明 akshare 数据准确、自研算法正确。

### 3.2 开盘啦

- 历史接口：`https://apphis.longhuvip.com/w1/api/index.php`
- 实时接口：`https://apphq.longhuvip.com/w1/api/index.php`
- 方式：POST 表单，无需登录 token
- 必带参数：`PhoneOSNew=1`、`DeviceID`、`VerSion=5.21.0.2`、`apiv=w42`、`Day`
- 成功标志：`errcode == "0"`
- 版本号不敏感，5.8.0.2 到 6.0.0.1 均可通过

| 接口 | `a` / `c` | 产出 |
|---|---|---|
| 情绪统计 | `HisZhangFuDetail` / `HisHomeDingPan` | 涨停跌停家数、ST 涨停、涨跌幅分档分布、情绪判语 |
| 打板列表 | `HisDaBanList` / `HisHomeDingPan` | 含**题材归因**、首封与开板时间、昨日连板、主力净额 |
| 梯队指标 | `ZhangTingExpression` / `HisHomeDingPan` | 情绪指标数组 + 文字判断 |

`HisDaBanList` 返回值是**位置数组**，字段靠下标定位：

```
[0]代码 [1]名称 [4]涨幅 [6]首封时间戳 [7]开板时间戳
[9]昨日连板文字 [10]昨日连板数 [11]题材 [12]主力净额
[13]成交额 [14]换手率 [15]实际流通
```

2026-08-03 情绪统计实测：涨停 83、跌停 9、ST 涨停 8、上涨 4005 家、下跌 1466 家，判语「市场人气高涨」。

### 3.3 备用与已否决

**同花顺涨停揭秘**（`data.10jqka.com.cn/dataapi/limit_up/limit_up_pool`）零鉴权可用，返回 100 条含 `limit_up_type`（换手板/一字板/T字板）、`limit_up_suc_rate`（封板成功率）、`open_num`（开板次数）。

但**题材质量不合格**，作为主源否决。它的 `reason_type` 是概念标签堆叠而非涨停原因，例如中瓷电子给「CPO+电子陶瓷+央企+一季报增长」，无法分辨当天的真实驱动。对比开盘啦同期给出的「可控核聚变、一带一路」「宇树机器人、机器人概念」「AI应用、DeepSeek」，后者主线明确。

板型和封板成功率这两个字段仍有参考价值，可作为补充。

**交易所官方**（降级为校验用）：

- 上交所 `http://yunhq.sse.com.cn:32041/v1/sh1/` 下的 `list/exchange/equity`（全市场 2351 只，单次 0.76 秒）、`dayk`、`line`（分时含竞价，首根 `93000` 即撮合结果）
- 深交所 `getTimeData`（单只，含五档）、`getHistoryData?cycleType=32`（历史日 K）
- 深市历史日 K 字段顺序（算术反推确认）：`[日期, 开, 收, 低, 高, 涨跌额, 涨跌幅, 成交量, 成交额]`
- 公告：巨潮资讯（证监会指定披露网站，沪深统一）、上交所公告接口（带 `BULLETIN_TYPE_DESC` 分类）、深交所 `annList`

## 四、已知的坑

### 4.1 深交所没有全市场批量行情接口

翻遍报表和 API 后确认。`1815_stock_snapshot` 等报表 HTTP 通但 `recordcount` 恒为 0（属收盘后日报，非盘中快照）；`1110` 是 A 股列表（2894 只），只有板块、上市日期、股本、所属行业等**静态信息**，不含行情。

深市逐只轮询实测：8 线程为吞吐甜点，14.2 只/秒，全市场约 198 秒、65 MB；16 线程反而降到 9.9 只/秒，说明服务端有节流。

这是当初放弃官方源的重要推力，现已不影响——akshare 一个请求解决。

### 4.2 涨停价计算不能用内置 `round()`

Python 的 `round()` 是银行家舍入，且受二进制浮点表示影响，`round(1.005, 2)` 得 `1.0`，会导致涨停价差一分钱，进而使涨停判定、一字板识别、连板计数全线错误。

必须用 `Decimal` 配 `ROUND_HALF_UP`。已在 `ultraboard/limits.py` 中处理。

### 4.3 开盘啦的两个限制

**实时接口有反爬。** `apphq` 的 `DaBanList` 返回的数组每个元素都是字符串 `"kaipanla.com"`，是占位符而非真实数据。历史接口无此问题。

**当日数据 18:00 后才准确。** 18:00 前查当日会返回 `errcode 1020 参数出错`，查 T-1 正常。这与复盘流程天然契合。

### 4.4 其他

- **B 股会混入涨停扫描**。`900915 ST中路B` 被误判涨停（成交额 0，量能比 6.33 倍失真）。900/200 开头必须排除。
- **深交所 `change20PerLimit` 不能用来判断涨跌幅档位**。曾假设它区分 10% 与 20%，实测宁德时代、东方财富等创业板返回的也是 `False`，与主板一致。涨跌幅档位只能按代码前缀加 ST 标记自行维护。
- **上交所 `tradephase` 首字母是交易阶段码**。实测 2350 只为 `E`（闭市）、1 只为 `P`（停牌）。开盘集合竞价应为 `C`、连续交易为 `T`，尚未实盘确认。

## 五、采集架构

### 5.1 两个采集时点

**每日 18:30，复盘采集（主）**

顺序拉取开盘啦当日数据与 akshare 四池，落 SQLite，只进不出。全程十几个请求。产出：题材属性、连板梯队、情绪温度、次日候选池。

**次日 09:25，竞价采集**

只采候选池（约 150 只）的竞价价量。属性昨晚已锁定，此处只补价量。实测 akshare 与东财在此规模下约 10 秒一轮，300 秒窗口内可反复采集与交叉验证。

### 5.2 访问策略

开盘啦是单点依赖（无 Tushare 备份通道），需按正常客户端的行为特征访问。四条原则：

1. **DeviceID 固定**。生成一次存本地，永久复用。开源爬虫每次请求都随机生成 UUID，而真实 APP 的设备号终生不变——同一 IP 后面冒出几百个设备号是最明显的爬虫特征。
2. **拉过的日期不重拉**。先查库再决定是否发请求。历史数据不变，可砍掉绝大部分请求量。
3. **每日固定时间单次采集**，请求间留数秒间隔。
4. **失败即停，不重试轰炸**。当日拉不到就次日补。

不做代理池与指纹对抗：一是对方改一次签名就得跟一次，维护成本超过数据价值；二是本项目的真实用量远达不到需要对抗的强度。

### 5.3 落库优先

无备份通道的情况下，**数据落库比任何反爬技巧都重要**。拉到即存，攒三个月即形成一份不可替代的历史题材归因库。接口日后失效、改版或加签名，历史数据仍在，回测不受影响。

同时这直接支撑案例复盘需求——任意一天的梯队与题材可随时还原。

## 六、待验证

| 项 | 说明 | 何时可验 |
|---|---|---|
| 竞价源选型 | 东财与交易所在 9:25~9:30 谁先更新竞价结果、最早哪一秒可得 | 需开盘实测 |
| `tradephase` 竞价态 | 确认开盘集合竞价阶段的字母码 | 需开盘实测 |
| 开盘啦回溯深度 | 历史能拉到多久，决定能否一次性灌入历史库 | 随时 |

| `HisDaBanList` 的 `Type` | 各取值含义未定，`Type=4` 疑为炸板/开板列表 | 随时 |

量能基准是待确认项中最要紧的一个。当前实现暂用"连板启动前 5 日均量"，2 倍以上为爆量、0.6 倍以下为缩量，**这只是能跑起来的默认值，不代表实际体系**。按打法描述，真实基准更可能是前一个板的量，或该股自身的历史地量与天量区间。

## 七、明确不做

- 不 fork 现有开源项目。考察过 [dragon-quant](https://github.com/sunshanggege/dragon-quant)（12007 行，分层干净，评分层不碰数据源）与 [vibe-astock](https://github.com/simonlin1212/vibe-astock)（12383 行，平铺结构，46 个文件中 11 个直接引用 akshare）。二者能白嫖的仅为缓存、存储、日志、回测、看板等通用基建，而最需要的数据层与连板评分层均无法复用，竞价环节两者都没有。**只借鉴设计，不继承代码。**
- 不做实时行情。项目定位为延迟容忍。
- 不做自动下单。打板确认由人工执行。

值得借鉴的两点设计：dragon-quant 的"门槛加权两段式聚合"（任一维度低于门槛即一票否决，通过者再加权排序），契合梯队卡位中"某条件不满足则整个梯队不做"的逻辑；vibe-astock 的晋级率分档统计（1进2 / 2进3 / 3板以上）与梯队断层检测。

### 已实现

| 模块 / 入口 | 说明 |
|---|---|
| `python -m ultraboard.kaipanla.backfill` | 开盘啦历史回灌 → `data/kaipanla/raw/YYYY-MM-DD/`（zt_pool / sector_ladder / sentiment / expression） |

| `python -m ultraboard.review.ladder_daily` | 涨停梯队逐日变化 + 跟随链 → `data/kaipanla/ladder_daily/` |
| `python -m ultraboard.review.ladder_selector select DATE` | 第一阶段节点日统一选层，不读 T+1 |
| `python -m ultraboard.review.candidate_initial_score DATE` | 冻结梯队内自然票自身证据 + 预期 PK → 次日竞价预期分 E，不读 T+1 |
| `python -m ultraboard.review.auction_score review DATE --fetch-missing` | 显式后验以开盘强度 + 实际层内 PK 计算 A、Δ 和独立收盘结果 |
| `python -m ultraboard.review.auction_score backtest --labels PATH --fetch-missing` | 跨节点后验校准，不向节点入口倒灌 |
| `ultraboard/kaipanla/client.py` | 开盘啦 HTTP 客户端（固定 DeviceID、间隔） |
| `ultraboard/limits.py` | 涨跌幅 / 一字 OHLC 判定等**校验工具**（非主采集） |
