# Agent 数据接口使用与经验

本文说明其他 Agent 如何低成本取得 Ultra-Board 事实。详细字段与错误码见
《单交易日事实接口契约》。

## 1. 核心原则

一次请求只承载一个交易日。默认日响应用于快速扫全局，个股重型字段和故事按需
批量拉取。接口只提供事实，不输出交易判断。

首板始终在默认日响应中，不存在“默认二板以上”或“按开关展开首板”的模式。

公网使用时，直接把完整的 `https://<host>/api/v1` 地址交给具备网页读取能力的
Agent。该入口返回所有端点的绝对地址、调用顺序、健康检查、使用指南和 OpenAPI 地址；
调用方只需能够执行公网 HTTPS GET 请求，不依赖本地文件访问能力。

## 2. 推荐调用顺序

### 第一步：确认数据已经正式发布

```http
GET /api/v1/health
```

只有以下条件同时成立才能继续：

```json
{
  "data": {
    "status": "ready",
    "publication_ready": true,
    "export_mode": "release"
  }
}
```

正式接口没有 partial stories 模式。
导出过程先完成全部日期校验再原子替换公开目录；失败不会生成半套新修订。

### 第二步：选择交易日

```http
GET /api/v1/calendar
```

只能从 `available_dates` 选择日期。要向前或向后观察，替换后续请求的 `date`；
不要一次请求多日，也不要按自然日猜交易日。

### 第三步：读取单日概览

```http
GET /api/v1/day?date=2026-07-24
```

默认返回当日题材故事和全部来源股票，包括全部首板和高板。每只股票只提供：

- `code`
- `name`
- `boards`
- `board_type`
- `main_theme`
- `themes`
- `first_limit_time`

代码不是展示细节，而是后续详情定位的稳定主键，因此始终保留。

题材故事位于 `day.theme_stories`，默认返回来源顺序、标题和故事原文，但不会携带
故事中的个股详情。题材故事 `context` 不能覆盖开盘啦个股题材。

### 第四步：按题材或梯队缩小范围

```http
GET /api/v1/day?date=2026-07-24&theme=智能电网&board=1
```

```http
GET /api/v1/day?date=2026-07-24&theme=AI应用&theme=机器人&theme_match=all&min_board=2
```

`theme` 精确匹配开盘啦主属性或候选属性，不做模糊匹配。多个题材默认任一命中；
需要属性交集时显式传 `theme_match=all`。

`board` 可重复选择精确梯队；`min_board` 与 `max_board` 用于连续范围。精确板数
与范围不能混用。题材和梯队同时存在时取交集。

### 第五步：一次批量获取需要的个股详情

```http
GET /api/v1/stocks?date=2026-07-24&code=600123&code=000001
```

代码和名称可以重复且可以混用：

```http
GET /api/v1/stocks?date=2026-07-24&code=600123&name=某某股份
```

接口按代码去重，返回每只股票完整的开盘啦属性、同花顺 `limit_facts` 与一个或多个
个股故事。名称只能精确匹配；不能唯一定位时必须改用代码。

批量请求是原子的。任何一个选择器不存在、任何一只股票的故事缺失或正文为空，
整批失败。调用方不能把失败项静默删除后继续分析。

## 3. 为什么采用两层响应

原始 `limit_pool` 为每只股票携带价格、市值、换手、封单、终封、开板次数、板型、
连板日期等大量字段；故事又包含长文本。如果它们跟随全市场股票默认返回，会让 LLM
在还没选定研究对象前就消耗大量上下文。

概览层保留题材故事以及第一眼必须看到的个股事实：名字、梯队、板型、题材和首封时间。详情层不删除
任何数据，只把读取时机推迟到 Agent 已经选出具体股票之后，并允许一次拉取多只，
避免逐只请求。

## 4. 参数组合速查

| 目的 | 请求 |
| --- | --- |
| 当日全市场 | `/day?date=T` |
| 某题材全部梯队 | `/day?date=T&theme=A` |
| 两个题材任一命中 | `/day?date=T&theme=A&theme=B` |
| 同时具有两个题材 | `/day?date=T&theme=A&theme=B&theme_match=all` |
| 只看首板 | `/day?date=T&board=1` |
| 一板和二板 | `/day?date=T&board=1&board=2` |
| 二板以上 | `/day?date=T&min_board=2` |
| 题材 A 的二至四板 | `/day?date=T&theme=A&min_board=2&max_board=4` |
| 多代码详情 | `/stocks?date=T&code=000001&code=600000` |
| 代码与名称混合详情 | `/stocks?date=T&code=000001&name=某某股份` |

## 5. 返回结构的使用边界

### `information_cutoff`

每个事实响应都必须携带。调用方不得把更晚日期的数据、新闻或人工标签倒灌到该日。

### `scope`

完整记录本次题材、题材组合方式、精确板数和板数范围。保存下游结论时应同时保存
`scope`，避免把筛选后的集合误当作全市场。

### `navigation`

只给前后可用日期，不包含对应日期的股票事实。继续观察时重新调用 `/day`。

### `data_revision`

同一轮任务使用的数据应保持同一修订号。修订号变化后，不要把两版数据拼成同一
事实集合。

## 6. 故事不是可选数据

日概览不展示个股故事，是为了减少上下文，不是允许缺失。

- 故事缺失的日期不能正式发布；
- `/stocks` 中 `stories` 必须为非空数组；
- 一个股票可以对应多个故事，必须全部返回；
- `context` 只是同花顺标题上下文，不是个股题材；
- 故事不能覆盖开盘啦 `theme/themes`；
- 不允许用新闻、默认文案或其他来源补造缺失故事。

## 7. 来源真相

| 字段 | 唯一来源 |
| --- | --- |
| 个股主属性和候选属性 | 开盘啦 `theme/themes` |
| 板数、板型、封板时间、价格、市值、换手、封单 | 同花顺 `limit_pool` |
| 板块与个股故事 | 同花顺 `stories` |
| 外部政策、公告和新闻上下文 | `/news/sources` 白名单 |

同花顺 `reason_type`、故事标题的 `context`、新闻关键词和人工关键词都不能覆盖
开盘啦题材。

## 8. 新闻白名单

先读取：

```http
GET /api/v1/news/sources
```

必要时校验具体地址：

```http
GET /api/v1/news/validate?url=https%3A%2F%2Fwww.csrc.gov.cn%2F
```

只允许 HTTPS 精确主机名。每次重定向后的地址都要重新校验。接口只校验地址，
不代理新闻正文。

## 9. 长期维护经验

1. 单日概览是唯一默认上下文，并默认展示题材故事，不再组装五日大包。
2. 首板是默认事实，不设计首板展开开关。
3. 详情分层不能变成数据裁剪；完整事实仍由 `/stocks` 原子返回。
4. 个股可以有多个动态属性，题材筛选必须保留主属性与候选属性。
5. 日期、题材和梯队是查询维度，不是分析标签。
6. 名称只做精确便利查询，代码是稳定标识。
7. 参数非法、股票不存在或故事缺失都必须明确失败，禁止静默忽略。
8. 数据层永远不返回核心、强弱、对手、接力、反攻、评分、买点或最优解。
9. 修改参数语义时必须同步 `/meta`、`/guide`、OpenAPI、本文件和接口契约。
